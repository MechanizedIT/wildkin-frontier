## Current fresh-process runner versus historical API

`tools/art/test-trellis-local.py` called the full loopback API. Its request explicitly supplied guidance 7.5, texture guidance 1.0, texture rescale 3.0, and `mesh_simplify=faces/1000`; the installed service chose its pipeline (including 1024 cascade), performed latent denormalization/decode, then exported.

`tools/art/trellis-process-staged.py` is intentionally different: one hidden fresh child per stage, CPU tensor/RNG handoffs, offline local cache, 512-only `low_vram` pipeline, steps 1–12, 30k export target, fixed 1K texture, no remesh, 32,768-coordinate limit, 750k **decoded-before-export** face refusal, 6GiB reserve, and 8GiB pre-`o_voxel` condition. It directly samples sparse/shape/texture latents and calls `decode_latent(shape, texture, 512)`. Installed `sample_shape_slat` performs shape-latent denormalization before the staged handoff; `decode_latent` itself does not apply that shape normalization step. It does not currently expose the historical full-API guidance/rescale controls; that is an intentional constrained experiment, not verified equivalence.

The earlier 7M face result could arise from input occupancy/latent topology, from the direct staged path differing from the service defaults, or both. It is not evidence that the 30k export target was ignored: `o_voxel.to_glb(... decimation_target=faces, remesh=False)` lies after decoder extraction. No comparison can identify a single causal error because Mossling has no recorded predecode count and the held Heartwood input differs.
