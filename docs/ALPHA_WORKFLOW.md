# Wildkin playable-batch loop — two-batch trial

September 13, 2026. Chris requested an independent comparison of Dream Loop, his earlier Rapid Alpha Producer skill and this project's actual results. This is a producer trial for the next two playable batches; shared skills used by other projects remain unchanged.

## Evidence to keep

- Explicit owners and separate review questions found real generation, clearance, asset and persistence problems in [regional blooms](../art/reviews/regional-blooms/process.md).
- An attainable locked target and independent judgment improved that bounded composition from 7.0→7.6→8.0. Keep this when appearance is the main uncertainty.
- Profiling before architecture changes produced measurable [streaming improvements](../art/reviews/streaming-preparation/receipt.md). Correctness work starts with a failing behavior; performance work starts with measurements.
- Disclosed fixtures, ordinary input and literal reload separate tested mechanics from earned outings. Keep those distinctions.

Rapid Alpha Producer offers useful batching and evidence-reuse ideas; its effectiveness in the earlier project is unverified here. Dream Loop's threshold is also insufficient by itself: [province terrain](../art/reviews/regional-provinces/receipt.md) stayed held after three rounds. Repeated structural gaps require a different approach or deferred polish, rather than more small color/scale changes.

## The loop

1. **Choose one playable outcome.** Group one to three related slices around visible player success/failure. Name owners, uncertainty and the exit in CURRENT_SLICE; avoid a status document per subtask.
2. **Establish the right baseline.** Use an actual short journey for interaction, a failing contract for correctness, timing for performance, or normal-camera images for appearance. Reuse feasible locked targets and unaffected evidence.
3. **Build and integrate early.** Root owns shared composition, canonical data, save schema and browser state. Workers get disjoint file chains; overlap independent recipe, visual or research work only when useful. Prove a representative effect before multiplying content.
4. **Review the principal risk.** One independent reviewer returns one consolidated repair packet. Use a visual judge for appearance, a specialist for save/physics/determinism, and both only when both risks materially changed. Root does not repeat a completed specialist investigation.
5. **Repair and reassess.** Rerun only invalidated proof. Default visual work gets one correction pass; a second needs a structural change. Reserve three rounds for a hero surface or major legibility risk. If the same gap repeats twice, stop that method, retain honest HOLD/debt and continue with a usable candidate under owner delegation.
6. **Play and checkpoint.** Complete one ordinary-input story per integrated batch. Freeze source and run the required aggregate/verify/ZIP once; retain focused failed-save and real Rapier proof where relevant. Check portable/offline behavior for the alpha candidate and changed loading/build surfaces. Update changed documentation and commit a cohesive batch on main. Push only under separate authorization.

## Dream Loop's job

Use it for a new hero place/creature, major terrain silhouette, camera/UI composition or failed normal-play readability. Build the target from the actual camera and admitted kit; check physical feasibility before production. Ask the judge for the three consequential gaps and an honest score. Actual gameplay owns scale/readability conclusions when a generated target is misleading. Ordinary save fixes, pure helpers, text and cache optimizations need no image target.

## Avoid observed waste

- Preserve valid journey segments when a harness endpoint, key timing or tool delay invalidates another segment. Repair the harness and repeat only affected proof; keep one complete fresh-player outing for the alpha candidate.
- Do not duplicate review questions or fill every worker slot. Parallel production needs nonoverlapping owners.
- Do not repeat aggregate checks after docs-only edits or every visual round. Group work into playable checkpoints without weakening repository requirements.
- Keep one compact receipt and actual evidence. Link old history instead of copying it into every restart document. Report player outcomes and limitations.

## Measure before claiming improvement

For each of the next two batches, record start/end time, completed player outcome, worker/reviewer roles, visual rounds, native journeys, aggregate runs and work repeated because of tooling or coordination. No new telemetry framework is needed. Compare useful outcomes and rework.

The review suggests repeated gates can add cost, but does not prove they dominate time; the latest aggregate took about 65 seconds. Browser/tool round trips, documentation and review handoffs also need observation. Retain or revise this trial after two batches. Never improve a speed metric by weakening save ownership, terrain support, deterministic caps or honest mobile/offline claims.
