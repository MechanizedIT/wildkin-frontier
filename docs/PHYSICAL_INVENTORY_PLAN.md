# Physical inventory implementation plan

September 11 — active producer plan, provisional implementation choices.

Owner direction: finite upgradeable backpack, draggable/sortable stacks, physical Camp storage, useful preparation within the crash-land exploration loop. Story obstacles and defended adjoining Camp sectors are active scope too; the inventory conversion must remain coherent across the existing whole game before those content additions depend on it. The independent narrative/system proposal is `CRASHLAND_PROGRESSION_PROPOSAL.md`.

## Current production order

**Review resolution:** use the small persistent active-run snapshot described in step4; do not impose recovery chores on mobile tab eviction. Existing one-time claims/resolved run IDs remain authoritative, with ordinary world actors rebuilt and paid unfinished tame attempts cleared. Resolve legacy building footprints before applying new sector/perimeter reservations. First sector uses explicit authored before/after barricade sets, outside the player-piece/refund economy. Keep one bounded outstanding yield per source; do not introduce an infinite field overflow bank. These are producer choices informed by independent review, not new owner-accepted balance.

1. Build small pure slot/stack operations and a findable item catalog for current resources and consumable gear. Provisional starting capacities: 16 pack slots, 24 pod/crate slots, later 20/24 pack upgrades; materials stack to 20, medicines/food to 5, taming gear to 3. Permanent Omni/construction actions keep their existing ownership. No weight/encumbrance or nested containers.
2. Keep one saved inventory authority under frontier progress. Convert old bank/medicine/field counters together; views may aggregate quantities but must never be independently spendable. Preserve surplus legacy quantities through an explicit finite withdraw-only physical delivery. Existing save/import versions, rollback and Author isolation are part of this conversion. Do not activate an incomplete grid over the existing infinite economy.
3. Integrate acquisition, partial chest rewards, gear use, station crafting, upgrades, building/refunds, repairs and campaign material rewards. Craft simulation consumes ingredients before checking output space and commits once. Costs use the pack plus one explicitly chosen nearby storage source. Full capacity must neither delete rewards nor duplicate claims/XP. Source-local uncollected rewards need bounded retention.
4. Preserve the same pack through departure and successful return; extraction secures XP/bonds/mission facts rather than depositing materials. Settle a small mobile reload/resume contract before runtime admission. Full AI/projectile serialization and elaborate anti-cheat are unnecessary; forced-loss/recovery on browser eviction remains a proposal under review, not an accepted rule. Death recovery and unique mission item preservation must be explicit.
5. Produce a Dream Loop inventory target from actual current UI, then implement 48px-or-larger cells, mouse drag and tap/keyboard alternatives, merge/split/sort, quantity feedback and full-pack handling. Show the physical locker/container and real contents; maintain input blocking, pause and responsive landscape/portrait behavior.
6. Prove one complete ordinary Camp→Verdant→return→unload/craft loop with finite capacity, one failed tame/retry, v2 migration with overflow, interruption/reload, save-write rollback and already-loaded offline behavior. Run focused tests during development and the aggregate at the integrated boundary. No claim that a helper test or static target establishes the playable inventory.
7. Add the first wreck-led blueprint/pack upgrade, unique fallen-growth passage, emergency Camp barricades and adjoining cleared yard. Use current IDs for saved repaired paths; preserve existing structures and route access. Generate and independently review relevant physical assets. Continue larger wreck progression after this useful first loop.
